# Журнал работ

## ЛР1. Стенд и сбор данных

### Решения по сборщику

- **Источник**: GH Archive — почасовые архивы
  `https://data.gharchive.org/<YYYY-MM-DD>-<H>.json.gz`, H без ведущего нуля.
- **Фильтр**: по полю `type` на стороне сборщика (источник фильтр не умеет);
  `PullRequestEvent,PullRequestReviewEvent,PullRequestReviewCommentEvent`.
- **Поток (`record`)**: позиция — последний успешно загруженный час в
  `data/raw/state/last_hour.txt`. Неполный/отсутствующий файл (404) не
  сдвигает позицию; сборщик возвращается к часу после `COLLECTOR_POLL_SECONDS`.
- **История (`backfill`)**: те же часовые файлы за 7 суток (11–17.10.2026),
  период в `COLLECTOR_HISTORY_FROM`/`COLLECTOR_HISTORY_TO`. `backfill`
  не пишет state — позиция потока не сбивается.
- **Раскладка**: поток — по `received_at` (`dt=/hour=`), история — по
  `event_time` (`dt=`). Так поздние события не дописываются в закрытые
  часы потока. Важно: файл `part-<получение>-<час события>.jsonl.gz` в
  `hour=22/` — это норма, если получен в 22:xx, даже если содержит события
  за 17:00 (задержка публикации источника).
- **Поля события**: `event_key` = `id`, `event_time` = `created_at`
  (UTC, ISO 8601), `received_at`, `source`, плюс `type`, `action`,
  `actor_login`, `repo_name`, `org_login`, `pr_number`, `pr_id`,
  `pr_state`, `pr_merged`, `public`. У `PullRequestReviewEvent` и
  `PullRequestReviewCommentEvent` номер PR берётся из
  `payload.pull_request.number` (в `payload.number` его нет).
- **Запись файла**: временное имя `.<stem>.jsonl.gz.tmp` → `rename` при
  закрытии. Незакрытых файлов под рабочим именем не остаётся.
- **Ротация**: `enforce_limit()` после каждого часа `record`; удаляются
  самые старые закрытые файлы, пока объём > `COLLECTOR_RAW_LIMIT_GB=20` ГБ.
  В `backfill` вызов один — после завершения цикла, чтобы не выбить
  свежие файлы `stream/`.
- **Повтор**: HTTP 429/5xx, `socket.timeout` и `URLError` — повтор с
  паузой 2^n (4 попытки в `fetch_hour`, пауза 1/2/4/8 с), затем
  `give_up_hour` и `hour_not_ready` с паузой `COLLECTOR_POLL_SECONDS`.
  `http.client.HTTPException` (обрыв HTTP посреди тела) обрабатывается
  как `incomplete_file`: `tmp` удаляется, попытка повторяется.
- **Дедупликация по `event_key`**:
    - внутри каждого часа — множество `seen_keys`, повторный ключ
      пропускается со строкой журнала `dedup_in_file`;
    - между часами — поиск `part-*-<hour>.jsonl.gz` через `rglob`
      по корню всего слоя (`stream/` или `history/`), а не только
      внутри текущего `hour=<получение>/`. Лог `skip_existing_hour`.
      Так перекачка часа после ручной правки `state` не создаёт
      дубль: файл часа уже лежит в своём `dt/hour=`, второй
      экземпляр в другом `hour=<получение>/` не пишется.
- **Ожидание часа**: `record` пробует скачать час сразу после его
  окончания (`if next_hour >= now: wait`). Если GH Archive ещё не
  опубликовал файл (404) — `hour_not_ready`, пауза, повтор. State не
  сдвигается.
- **Память**: файл читается потоком через `gzip.GzipFile(fileobj=resp)`,
  ответ не буферизуется целиком. Работа в пределах 512 МБ.
- **Метрики** (допзадание): `:9101/metrics` в формате Prometheus —
  `collector_events_total`, `collector_errors_total`,
  `collector_last_success_timestamp_seconds`. Метка `mode` отражает
  фактический режим процесса (`record` или `backfill`), а не значение
  `COLLECTOR_MODE` из `.env`.
- **State после рестарта**: `SIGTERM` → graceful shutdown (2–5 с),
  при старте читается `last_hour.txt`, повторно скачанные часы
  пропускаются по имени файла.

### Допзадание: счётчики на 9101

- Метрики: `collector_events_total`, `collector_errors_total`,
  `collector_last_success_timestamp_seconds` в формате Prometheus.
- Демонстрация роста `errors_total`:
    - до: 0;
    - заблокировали HTTPS внутри netns контейнера:
      `nsenter -t <pid> -n iptables -A OUTPUT -p tcp --dport 443 -j REJECT`;
    - в логе: `url_error "Network is unreachable"` с `pause=1, 2, 4, 8`
      (4 попытки в `fetch_hour` с экспоненциальной паузой), затем
      `give_up_hour` и `hour_not_ready` с паузой `POLL_SECONDS`;
    - во время: `errors_total` растёт на 1 за каждый неуспешный retry
      (для часа, все попытки которого провалились, — **+4**);
      `give_up_hour` и `hour_not_ready` счётчик не увеличивают,
      `incomplete_file` добавляет ещё 1;
    - после снятия блокировки: `errors_total` остаётся прежним
      (монотонный), `poll` восстановился, `last_success` обновился.

### История остановок и догонов

- **18.10.2026 18:50 UTC** — ручная остановка (`state = 2026-10-18-18`,
  в `stream/` 19 файлов). Возобновление 22.10 22:09 UTC: `record`
  догнал часы 18.10 19:00 → 22.10 21:00 (~99 ч).
- **Ошибочное удаление файлов догона 18–22.10**. Файлы вида
  `part-20261022T221655-20261022T17.jsonl.gz` в `dt=2026-10-22/hour=22/`
  были приняты за дубли и удалены. Это **не дубли**: `hour=22` —
  партиция по `received_at`, а `-17` в имени — `event_time`. Восстановление
  отложено: `state` ушёл вперёд, `record` назад не пойдёт; при необходимости
  закрывается `backfill` в `history/` перед ЛР3.
- **23.10.2026 18:11 UTC** — обновление Docker, `SIGTERM`, graceful
  restart за 5 с. State прочитан, запись продолжена без потерь.
- **24.10.2026 22:23–22:24 UTC** — ручной стоп для демонстрации
  допзадания, state = `2026-10-24-21`, запуск с `state=2026-10-18-18`
  для форсирования HTTP-запроса, догон 18.10 19:00 → 24.10 22:00.
  Отключение сети через `nsenter … iptables REJECT` дало рост
  `errors_total`, после снятия блокировки сборщик восстановился.
- **25.10.2026** — исправлены `process_hour` (поиск уже скачанного
  часа через `rglob` по всему слою; раньше — только в текущем
  `hour=<получение>/`, что при сбросе `state` давало дубли в другом
  `hour=`), `normalize` (`pr_number` у review-событий из
  `payload.pull_request.number`), `enforce_limit` в `backfill`
  (один вызов после цикла), `incomplete_file`
  (ловит `http.client.HTTPException`). Проверено: при
  `state = 2026-10-19-05` сборщик пишет `skip_existing_hour`
  для 19.10 06:00.

### Ограничения

- `enforce_limit()` обходит всё дерево `data/raw/` через `rglob` —
  при миллионах файлов станет узким местом; заменить на очередь по `stat`.
- `state/last_hour.txt` не защищён от ручного редактирования — при ошибке
  сборщик пойдёт не с того места. Резервное копирование state перед
  экспериментами. С 25.10 частичный предохранитель — `skip_existing_hour`
  по `rglob`: перекачанный час не создаёт дубль, но и не заменяет старый
  (если тот был неполным).
- История не обновляется автоматически; для восполнения пропусков
  потокового слоя повторять `backfill` за нужные сутки.

## ЛР2. Форматы данных

### Схема Avro

- `schemas/event.avsc` (v1) — 14 полей паспорта. Обязательные: `event_key`,
  `event_time`, `received_at`, `source`, `type`. Остальные nullable с default null.
- `event_time` и `received_at` — `long` с `logicalType: timestamp-millis`,
  UTC. Конвертация ISO 8601 → мс в `schemas/check.py:iso_to_ms`.
- Схема v2 (`event_v2.avsc`) добавлена полем `review_state` (`null|string`,
  default null). Версии v1 и v2 — разные коммиты.

### DuckDB: типы и повторы

- `read_json_auto` вывел: `event_time` и `received_at` — `VARCHAR`
  (строки ISO 8601); `pr_number` — `BIGINT` (бывает null); `pr_merged`,
  `public` — `BOOLEAN`; `pr_id` — `BIGINT`.
- Отличие от схемы: DuckDB не парсит ISO 8601 сам, приведение
  `CAST(... AS TIMESTAMP)` делается в `to_parquet.sql`. В схеме Avro
  время — `timestamp-millis` (long), поэтому в `check.py` конверсия ISO→мс.
- `dup_keys = 0` (проверено `count(*) - count(DISTINCT event_key)`).
- Всего событий в наборе (stream + history, консистентно): **649 826**
  за 15 дат (`event_date` 11.10–25.10). Из них:
    - `history/` (11–17.10, backfill): **350 844** — совпадает с ЛР1;
    - `stream/` (18–25.10, `record`): **298 982**.
      Разбивка по датам — в таблице «Шаг 9» ниже.

### Parquet

- `to_parquet.sql`: `data/duckdb/parquet/events/event_date=…/part-*.parquet`.
  Партиция — `event_date` по `event_time` UTC (не по `received_at`).
- `OVERWRITE_OR_IGNORE true` + `FILENAME_PATTERN 'part-{i}'` — повторный
  запуск перезаписывает те же файлы в тех же партициях, копий не появляется.
- Объём: raw = **28 МБ** (stream 13 + history 15), parquet = **33 МБ**.
  Parquet (snappy) на 18% больше raw (gzip) — причины ниже, в разделе
  «Объём». Сжатие «в лоб» не работает: snappy слабее gzip для JSON-ключей.

### Замеры raw vs Parquet

Запрос: число событий по часам за 22.10.2026 в разрезе `type`.
Медиана трёх прогонов (`.timer on`, `real`).

| Путь                                | 1-й, с | 2-й, с | 3-й, с | **Медиана, с** |
| ----------------------------------- | ------ | ------ | ------ | -------------- |
| raw (gzip-JSON, stream + history)   | 4.971  | 3.590  | 3.529  | **3.590**      |
| Parquet (snappy, hive_partitioning) | 0.022  | 0.016  | 0.018  | **0.018**      |
| ускорение                           |        |        |        | **~200×**      |

Ответы совпали (72 строки = 24 ч × 3 type).

### Объём

| Каталог                      | du -sh    |
| ---------------------------- | --------- |
| `data/raw/stream`            | 13 МБ     |
| `data/raw/history`           | 15 МБ     |
| `data/raw` всего             | **28 МБ** |
| `data/duckdb/parquet/events` | **33 МБ** |

Parquet (snappy) на 18% **больше** raw (gzip), но в 200 раз быстрее
на запросе за сутки. Причины размера:

- raw сжимает повторяющиеся ключи JSON (gzip ×7–8 эффективнее snappy);
- в Parquet 15 файлов × overhead метаданных (~50–100 КБ на файл);
- колоночное хранение разреженных строковых колонок.

Скорость даёт партиционирование: raw требует распаковки всех ~330
файлов, Parquet отсекает 14 из 15 партиций по метаданным. zstd
(допзадание) даст ~2× меньше по объёму при той же скорости.

### Совместимость

- v1 → v2 (backward): `errors_total = 0`, поле `review_state` = null в
  прочитанных записях (default).
- v2 → v1 (forward): `errors_total = 0`, поле `review_state` отбрасывается
  v1-читателем (Avro не падает на неизвестных полях).
- Вид совместимости: **Full** (добавление поля с default в Avro совместимо
  в обе стороны).
