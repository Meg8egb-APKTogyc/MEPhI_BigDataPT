### Допзадание: полный лог роста счётчика ошибок

**До блокировки:**

```text
collector_errors_total{mode="record",kind="http"} 0
```

**Блокировка HTTPS внутри netns контейнера:**

```bash
nsenter -t <pid> -n iptables -A OUTPUT -p tcp --dport 443 -j REJECT
```

**В журнале:**

```json
{"level":"warn","msg":"url_error","error":"Network is unreachable","pause":1}
{"level":"warn","msg":"url_error","error":"Network is unreachable","pause":2}
{"level":"warn","msg":"url_error","error":"Network is unreachable","pause":4}

{"level":"warn","msg":"give_up_hour", ...}
{"level":"info","msg":"hour_not_ready", ...}
```

**Счётчик во время блокировки:**

```text
collector_errors_total{mode="record",kind="http"} 4
```

**После снятия блокировки:**

```text
collector_errors_total{mode="record",kind="http"} 4
collector_last_success_timestamp_seconds 1768212011
```

`errors_total` монотонный, poll восстановился, `last_success` обновился.  
`give_up_hour` и `hour_not_ready` счётчик не увеличивают; `incomplete_file` добавляет ещё 1.

### Проверка «no copies»: детали

Два прогона `to_parquet.sql` подряд:

- число `.parquet`-файлов: **15 → 15**, копий (`part-1.parquet` и т.п.) не появилось;
- `binary-md5` каждого файла меняется — из-за параллельного `read_json_auto` (порядок строк недетерминирован) и метаданных Parquet. Это не признак изменения данных;
- content-hash по партиции  
  `md5(string_agg(event_key, ',' ORDER BY event_key))`:  
  для всех 15 дат (11.10–25.10) совпадает до и после прогона  
  (`diff content_before.csv content_after.csv` — пусто).

Логическое содержимое не изменилось, повторный запуск идемпотентен. После проверки повторно запущен `to_parquet_v2.sql` — в партиции `event_date=2026-10-25` колонка `review_state` содержит реальные значения (**617 непустых**) и `NULL` у файлов до правки `main.py`.

### Замеры: полные прогоны

| Путь                                  | 1-й, с | 2-й, с | 3-й, с | Медиана, с |
| ------------------------------------- | -----: | -----: | -----: | ---------: |
| raw (gzip-JSON, `stream + history`)   |  4.971 |  3.590 |  3.529 |  **3.590** |
| Parquet (snappy, `hive_partitioning`) |  0.022 |  0.016 |  0.018 |  **0.018** |
| **Ускорение**                         |        |        |        |  **~200×** |

Ответы совпали (**72 строки = 24 ч × 3 type**).

**Объём:**

| Каталог                      | `du -sh` |
| ---------------------------- | -------: |
| `data/raw/stream`            |    13 МБ |
| `data/raw/history`           |    15 МБ |
| `data/raw` всего             |    28 МБ |
| `data/duckdb/parquet/events` |    33 МБ |

Почему Parquet больше: raw сжимает повторяющиеся ключи JSON (gzip ×7–8 эффективнее snappy); в Parquet 15 файлов × overhead метаданных (~50–100 КБ на файл); колоночное хранение разреженных строковых колонок. Скорость даёт партиционирование: raw требует распаковки всех ~330 файлов, Parquet отсекает 14 из 15 партиций по метаданным.
